# 灵感助手 · 从灵感到项目：全过程与设计思路

> **一句话定位**：在灵感进入昂贵大模型之前，先把它"洗"成 AI 爱喝的水。
> 用户负责随口说，系统负责结构化，高端 AI 只负责最后的创作。

---

## 零、为什么需要这样一套过程

普通人的思考是**非线性、口语化、碎片化**的：一次说一堆、重复、跑题、语气词满天飞。
而高端大模型的计费方式是**按 token 线性计费**的：口语废话越多，钱烧得越快；结构越乱，模型越容易跑偏。

这两者之间存在一个**结构性错配**。本项目的全部设计，都是为了在这个错配的位置插入一个"预处理车间"：

```
思考（混沌，免费） → 【预处理车间】 → 提示词（结构化，值钱） → 大模型（昂贵）
```

**核心公式**：`成本 = token 数 × 单价`。单价不可控，**token 数可控**。
所以设计思路只有一句话：**把成本控制在输入端，而不是在输出端后悔。**

## 一、全景链路：六个阶段

一个灵感从诞生到变成项目文件，要穿过六个阶段。前五个是系统做的，第六个是用户拿着成果去做的。

| 阶段 | 名称 | 由谁触发 | 产出物 |
|---|---|---|---|
| 0 | 捕获 Capture | 用户（随手说） | 一条原始大白话 |
| 1 | 清洗 Clean | 系统自动 | 一段精炼文本 |
| 2 | 沉淀 Persist | 系统自动 | 一条结构化记录（挂到某项目） |
| 3 | 累积 Accumulate | 时间（自然发生） | 一组带主题倾向的记录集 |
| 4 | 整合 Consolidate | 用户（点按钮） | N 条收敛为 M 条（M ≤ N）的需求集 |
| 5 | 合成 Compose | 系统自动 | 一份 MD 项目文件 |
| 6 | 消费 Consume | 用户（投喂） | 高端 AI 产出的真实项目 |

### 阶段 0 · 捕获（Capture）

- **目标**：让"记录"这件事的摩擦力降到 0。
- **输入 → 处理 → 输出**：灵感在脑子里 → 不做任何要求地倒出来 → 一段大白话文本。
- **设计思路**：
  - **绝不在这一步要求用户结构化。** 一旦要求"请填写标题、分类、优先级"，记录行为就死了。人只在"随便说"的时候才愿意说。
  - 项目维度的选择放在**输入框上方**（选 A 项目 / B 项目），而不是让用户描述"这是关于哪个项目的"——**结构化靠 UI，不靠语言**。
- **失败模式**：用户懒得打开工具 → 对策：入口要浅（一个输入框 + 一个按钮），未来甚至可以做语音输入、浏览器插件随写随存。

### 阶段 1 · 清洗（Clean）

- **目标**：**语义不变，冗余归零。**
- **输入 → 处理 → 输出**：原始口语 → 去噪 + 保义 + 重组 → 精炼文本。
- **具体要做的四件事**：
  1. **删冗余**：语气词（呃/嗯/啊/对吧）、口癖（那个/就是说）、重复句（"只会用大白。只会用大白话。"）
  2. **补结构**：把一锅粥的一句话流，按语义切成几条并列要点
  3. **保语义**：删除和改写都不得改变意图，不得添加用户没说的内容
  4. **控长度**：目标压缩率 60%–80%，但不为了短而丢信息
- **设计思路**：
  - **清洗是"翻译"，不是"创作"。** 提示词里必须写死"只输出正文，不要解释"，否则模型会给你加一段"好的，我来帮你整理："——那又是被计费的废话。
  - **这一层天然是双档的**：规则引擎（快、免费、能删词）与大模型（慢、花钱、能懂语义）。**规则先兜底，模型做增量**——这正是本项目 "mock / 模型" 双模式的由来。
- **失败模式**：
  - 规则清洗删过头、把话删残 → 对策：保留原始文本，随时可回看对照。
  - 思考型模型把 token 全花在推理上，正文为空 → 对策：关闭 thinking、加大 max_tokens、解析层做空值兜底。

### 阶段 2 · 沉淀（Persist）

- **目标**：把"一次性的对话"变成"可累积的资产"。
- **输入 → 处理 → 输出**：精炼文本 → 写入对应项目的记忆库 → 一条带时间戳的记录。
- **设计思路**：
  - **记忆库按项目隔离**（一个项目一张账本）。项目是天然的心智容器——人对"我在做几件事"是有清晰边界的，产品结构要顺着这个心智，而不是逆着它。
  - **原始文本与精炼文本同时保留**。前者是"证据"，后者是"资产"。永远不要为了整洁而销毁证据——用户对你的信任，建立在他能随时验证"你到底改了我什么"。
  - **写入即成功**。清洗失败不能阻断记录（降级存原文），因为丢失灵感比清洗不完美严重得多。
- **失败模式**：数据库成了孤岛，用户不敢用 → 对策：所有内容都是纯文本，随时可导出，不做数据锁定。

### 阶段 3 · 累积（Accumulate）

- **目标**：让零散的记录**自己长出结构**。
- **输入 → 处理 → 输出**：一条条独立记录 → 时间与重复自然形成聚类 → 一个"看起来零散、其实有主题"的集合。
- **设计思路**：
  - **不在记录时做分类，在整合时再聚类。** 记录时让用户选分类，等于逼他当场做判断——成本太高、还容易选错。分类是"事后站在高处看"才能做好的事。
  - 这一阶段系统**什么都不用做**，它的价值是"允许用户在一个月里漫无目的地输入 10 条"。**不打扰，本身就是功能。**
- **失败模式**：灵感之间差异太大，整合不出东西 → 对策：整合结果允许"合并失败"，允许原样保留，不强行产出。

### 阶段 4 · 整合（Consolidate）

- **目标**：把 N 条碎片收敛成 M 条**互不重复、彼此独立**的需求。
- **输入 → 处理 → 输出**：10 条相似/互补的记录 → 语义去重 + 合并同类 + 补全表述 → 7 条精炼需求。
- **设计思路**：
  - **判断标准要可解释**："语义相似度高于某阈值就合并"，宁可少合、不要错合。错合会永久丢失一个想法。
  - **合并要"信息不减"**：A 说"要能自动整理"，B 说"整理时按时间排序"——正确的合并是"自动整理，按时间排序"，而不是二选一。
  - **永远给用户对照视图**：左边 10 条原文，右侧 7 条结果。用户一眼看出"哪三条被合并了、有没有丢东西"，这是信任的关键。
- **失败模式**：模型擅自"优化"掉用户的想法 → 对策：提示词强调"只做去重与合并，不得添加新需求、不得删除独立需求"。

### 阶段 5 · 合成（Compose）

- **目标**：产出一个**能直接扔进任何高端 AI** 的项目文件。
- **输入 → 处理 → 输出**：结构化记录集 → 模板化编排 → 一份 `.md` 文件。
- **设计思路**（这一阶段最容易做出差异化，也最容易做砸）：
  - **选 MD 而不是 JSON/数据库导出**，三个理由：① 纯文本、人类可读、机器可读；② 大模型天生吃 MD；③ 用户能拿着它到处走，不受任何平台锁定。
  - **MD 不是数据倾倒，而是"提示词工程成品"**。一份好的导出文件应该包含：项目背景 / 核心目标 / 需求清单 / 约束条件 / 期望产出格式。用户拿着它，**不需要再想怎么提问**——这才是"帮不会写提示词的人"的最终交付。
  - **文件要有版本感**：导出的文件带时间戳，用户能看出"这版比上版多了什么"。
- **失败模式**：导出成一个大杂烩 → 对策：固定模板 + 分区小标题，AI 和人都能秒懂结构。

### 阶段 6 · 消费（Consume）

- **目标**：让用户拿着文件，**一次就把事办成**。
- **输入 → 处理 → 输出**：MD 文件 → 粘贴进高端 AI → 生成具体方案/代码/文案。
- **设计思路**：
  - **闭环必须在演示里被看见。** 产品的说服力不在"我洗了 10 条灵感"，而在"我拿着洗完的文件，让一个昂贵模型一次性产出了可用成果"。
  - 这一步也是**量化价值**的落点：同一段原话 vs 清洗后的文件，token 数差多少、省了多少钱，当场算给评委看。
- **失败模式**：用户不知道要投喂什么 → 对策：导出时附一段"建议这样用"的两行提示。

## 二、系统分层：这套过程落在代码里长什么样

过程是时间维度的，实现是空间维度的。同一个系统，横着看是六个阶段，竖着切是六个层：

| 层 | 名称 | 职责 | 对应技术 |
|---|---|---|---|
| L0 | 交互层 | 只负责"收"和"展示" | React + Vite + Tailwind |
| L1 | 编排层 | 决定"什么时候调谁"，不放业务逻辑 | FastAPI 路由 |
| L2 | 智能层 | 把"语义处理"抽象成可替换的能力 | Provider 抽象（mock / LongCat / 任意 OpenAI 兼容） |
| L3 | 记忆层 | 唯一真相源，持久化一切 | SQLite（Project / Inspiration / ModelConfig） |
| L4 | 输出层 | 把结构化数据编译成人话+AI 话 | MD 合成器 |
| L5 | 下游层 | 用户自己的昂贵模型 | 用户手动投喂 |

**四条分层纪律**（这几条决定了项目后期会不会变成屎山）：

1. **层间只走明确定义的接口**——L1 不关心 L2 用的是哪家模型，只调 `clean()` / `consolidate()`。
2. **智能层永远可替换**——换模型只改配置，不改代码。这是"不被任何一家模型绑架"的底层保险。
3. **降级路径必须存在**——没有 key、断网、限流时，系统要能退到规则清洗，而不是白屏。
4. **记忆层是单点**——所有内容落到同一个数据库，导出只是"投影"，不是"搬家"。

## 三、六条贯穿全局的设计思路

前面是"怎么做"，这里是"为什么这么做"——也是评委最会追问的部分。

| # | 思路 | 一句话解释 | 具体体现 |
|---|---|---|---|
| 1 | 成本前置 | 省钱要在输入端省 | 清洗、去重、压缩全部发生在投喂之前 |
| 2 | 零认知负担 | 不要求用户学会任何东西 | 大白话直入，结构化交给界面和系统 |
| 3 | 数据主权 | 用户的灵感必须能带走 | 纯文本存储 + MD 导出，不做锁定 |
| 4 | 智能可插拔 | 不被任何一家模型绑架 | Provider 抽象层 + 自定义 API 接入 |
| 5 | 降级可用 | 坏消息也要能跑 | mock 规则引擎兜底，断网也能演示 |
| 6 | 证据可回溯 | 改了什么，用户说了算 | 原文与精炼文同时保留、对照展示 |

## 四、工程实施路径：三个阶段推进

一个"有层次"的项目不是一次做完的，而是**一层一层长出来的**。每一层都要能独立跑通、独立演示。

### 阶段一 · MVP（打通主链路）
- **目标**：一个灵感进去，一条记录出来。
- **范围**：输入框 + 清洗（mock）+ 存库 + 前后对比展示。
- **验收**：断网状态下也能完整演示一遍。
- **工程要点**：先跑通，再谈架构；但目录结构一开始就要分层（`routers/` / `services/llm/` / `models.py`）。

### 阶段二 · 增强（补上"项目"与"智能"两个维度）
- **目标**：多项目沉淀 + 真实模型 + 整合。
- **范围**：项目侧栏与切换、历史记录列表、模型选择器（自定义 API）、去重整合、错误分类提示。
- **验收**：能对着一个真实项目积累 10 条灵感，一次整合收敛到 7 条，且结果可对照。
- **工程要点**：**接入真实模型的那一刻，就是"思考型模型返回空 content"这类边界问题集中爆发的时候**——解析层必须从第一行就写成防御性的。

### 阶段三 · 交付（合成与上线）
- **目标**：产出可投喂的成品 + 可访问的链接。
- **范围**：MD 合成与下载、模板化导出、前端部署（Vercel/静态托管）+ 后端部署（Render 等免费档）。
- **验收**：陌生人拿到链接，不看你操作，也能自己走完全流程。
- **工程要点**：部署前先做"离线包"演练——万一现场网络不可用，本地启动 + mock 兜底照样能演。

## 五、这套过程如何变成答辩故事

同样的技术，讲法不同，得分不同。把上面的链路翻译成"讲人话"的三段式：

1. **痛点（30 秒）**：普通人不会写提示词，只会说大白话；而大白话在按 token 计费的高端模型面前，是**真金白银的浪费**。
2. **方案（一句话）**：所以我们在中间放了一个"预处理车间"——**先洗干净，再喂给贵模型**。灵感随手记，系统自动整理，一个月后一键整合成项目文件。
3. **证据（现场演示）**：同一段原话，直接投喂 vs 经我们清洗后再投喂，**当场对比 token 消耗与产出质量**；最后把导出的 MD 文件投给高端模型，让它当场产出成果——**闭环落地，全场最有说服力的一击。**

**演示脚本（四步）**：
输入大白话 → 展示清洗前后对比 → 一键整合（10 条 → 7 条）→ 下载 MD 并投喂高端 AI 生成成果。

**评委追问的标准答案**：
- "这不就是个备忘录？" → 备忘录存原文，我们存**AI-ready 素材**，还能跨时间整合去重。
- "技术上有什么含量？" → 分层架构、Provider 可插拔、成本控制策略、降级设计。
- "数据安全吗？" → 全本地存储，灵感不离开用户电脑，可随时导出。
